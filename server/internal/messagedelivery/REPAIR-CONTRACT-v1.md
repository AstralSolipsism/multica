## 二、批准目标模型：同意新增，但批准必须指明来源

采用实施方的 `labrastro_message_approved_target` 及 owner/admin 批准、撤销 API。首版批准按自动化限定，唯一范围明确为 **workspace + autopilot + installation + 规范化 target_key**；增加 `autopilot_id`，避免“批准 A 自动化的分享目标”被 B 自动化借用。保留批准人、时间及可查的生效/撤销状态。API 文档明确：管理员此动作同时批准该自动化向该目标分享规则允许的结果内容；不暗含全工作区所有来源的分享授权。

群、话题继续使用当前规范化目标键；话题的真实 anchor→chat 关系仍须通过 pinned installation 验证。先保留精确目标批准，不在本轮增加通配群、通讯录或通用授权中心。现有未批准的群/话题路由不能在迁移中自动取得批准；记录为待批准并阻止实际外发，管理员批准后按既有生效窗口操作，不擅自补发旧消息。

保存、改目标、启用、test-send、worker 新发送和人工重试后的执行都必须经过同一授权组合：实际 acting member 的既有写权限、适用的批准范围、来源/工作区存续、installation 有效性、成员精确绑定或外部目标验证。发送时按 delivery **冻结的来源和目标**查批准，不能用修改后的 route 目标替旧内容取得授权。批准撤销后 queued 项取消；已认领者开始新发送前同样检查。平台已经接受的请求按回执记录真实结果，不能声称撤销可召回消息。

成员目标沿用现有成员、来源权限和 `(workspace, installation, user)` 绑定检查，可不进入群/话题批准表。需要纠正实施方案的一处理由：**绑定只证明接收地址归属，不等于来源分享授权**；本期自动化结果投递也不能引用后续“本人收件箱转发”功能作为授权依据。

共享 `CanWriteAutopilot` 保持原有 owner/admin、创建者、collaborator 语义；HTTP 继续通过既有 acting-human 判定入口获得真实发起人，不改成 runtime owner 或只允许人类调用。批准人的审计身份与持续执行授权主体保持区分。

## 三、来源和首次终态：同意修改共享 SQL，完整处理调用方

接受在 `UpdateAutopilotRunTerminalWithQuota` 增加非终态状态守卫：仅 pending/issue_created/running 可成为首个有效终结者。保留现有配额 CTE 同一事务结算；输掉竞争的调用按幂等 no-op 处理，不再次发布 run-done、不重复统计或结算。实际数据库错误仍是错误，不能统归为 no-op。核对全部生产终结调用点，不能留下仍使用无守卫旧 helper 的活跃路径。

成功和失败的 issue 终态都由 `SyncRunFromIssue` 写入结构化 `first_terminal_status`。可以继续使用 `run.result`，无需另建状态机；对失败分支写入时，只在本次同步确有结构化值时更新，避免普通 task 失败以空参数抹掉已有 result。保留可识别的状态键与既有自定义状态映射，外发不从任意失败字符串推导状态。

删除 `failure_reason` 的 `issue ` 前缀解析。任务原始错误仍可用于已有内部审计，正文仅采用明确可公开字段或通用失败说明。没有持久首终态证据的历史记录继续降级，不读取当前 issue 状态冒充历史；本轮不要求恢复无法知道的瞬时状态。

直接入队和 `decideMissing` 必须共用完整来源解析结果，包含 task_id、issue_id、result 及状态，防止两处独立拼接 DTO 再遗漏字段。已知来源依据 run 自身持久关系，空 output 仍按 run_only 显示无报告正文。陈旧来源查询去掉当前 `a.execution_mode` 过滤；无法证明原模式的历史行明确降级，不能把当前可变配置当作历史事实。

## 四、补偿扫描：接受持久游标，补齐周期和并发规则

接受 `labrastro_message_scan_cursor`，但应是**每种扫描器一行**，而不是三类来源共用一个全局位置：run_only terminal task、create_issue issue 状态、create_issue linked-task 最终失败各自推进。

每轮周期记录固定上界、当前位置与修订/代次；优先按不可变候选 ID 分页，而非会被反复修改的 updated_at。每 tick 有工作预算，达到预算时保存位置，下 tick 继续；到达该轮固定上界后重置，下一周期重新扫全体仍缺处理的持久来源。固定上界保证持续新增候选时旧周期也能结束，重置保证晚提交、旧键新变终态的来源仍被再次访问。

多副本用短期认领或 compare-and-set 保护游标推进/重置，过期执行者不能把位置写回旧代次。页面完成后再推进；中断允许重放页面，依靠终态守卫和决定去重保证幂等。游标缺失/不可用时从头重建，不以跳过来源恢复。不要跨页处理或外部请求长期持有数据库事务锁。

第三类扫描必须关联到仍活跃的 create_issue run，复用 `SyncRunFromLinkedIssueTask`，不能遍历普通无关任务。已有 `HasActiveTaskForIssue` 检查保留：还有活跃重试时不得提前判失败。三类扫描的单类失败不应永久阻止另两类得到处理机会。

## 五、统一普通投递、test-send 和重试

接受把 test-send INSERT 纳入 `withParentLock`，以及复用带 token 的结果写入；进一步把这些规则收在共用生命周期帮助函数中，避免再为 test-send 保留完整旁路。

可以保持现有同步 test-send API：在短事务中持 workspace 父对象锁，创建并取得属于该 ID 的有界认领，提交后执行共用发送路径；不能调用全局 ProcessNext 去随机处理其他投递。内部可先 queued 再按 ID 认领，但两步应在该事务内完成。test-send 可以有明确的诊断性条件差异，不能用一个提前 return 跳过来源授权、批准、installation 与租约校验。

全部投递结果写入统一核对 ID、lease token、sending 状态，并与到期语义一致；旧 owner 无权覆盖新 owner。发送每个新分片前检查仍拥有有效认领；超时或所有权丢失按 uncertain/恢复协议处理，不自动重跑自动化。脱离请求取消的有界结果写入继续保留，但必须同样遵守所有权约束。

已开始的外部请求晚返回时，可记录已有分片的真实外部回执；不能因此取得新发送权、覆盖新投递状态或在删除后重建回执。固定 UUID、已确认分片跳过与人工核实 uncertain 的规则保持。同步响应返回真实投递 ID/状态；若接口状态码有调整，随实际契约更新示例。

新批准记录、路由、delivery 和 receipt 的创建均需与对应 workspace 删除串行；批准表同时纳入自动化删除、installation 卸载和 workspace 清理。游标若为跨工作区共享表，应在 manifest 明确分类，不错误地归给任一工作区。

## 六、实施顺序与一次性交付

1. 将本版实施约定落入 PR 文档，并将第二次审阅的 8 个复现接入正常测试或稳定的集成测试入口。允许随接口调整适配测试装配，保留业务断言。先修 S2，确认夹具和清理错误都能影响测试退出码。
2. 完成批准表、游标表与所需索引的新增迁移、删除清单及 SQL 契约。使用实际可用的新编号和完整文件名，不改已应用迁移；独立 concurrent index、invalid-index 清理及 sqlc 约定保持。
3. 先完成共享授权、来源解析和原子终结，再接三类扫描与统一投递生命周期；逐步本地验证，不逐补丁请求外部复审。
4. 在同一最终 SHA 汇总修复和回归结果，再更新 PR 并发一次完整复审请求。提交数由可审阅性决定，不把“必须压成一个 commit”当验收条件。

## 七、统一验收矩阵

| 编号 | 必测场景 | 判定 |
| --- | --- | --- |
| A1 / R1、R2 | 普通协作者录入未批准目标；管理员批准；不同 workspace/installation/autopilot 复用批准；撤销后保存/启用/test-send/worker/重试 | 仅匹配批准范围且持续有权者可发，撤销后未发项停止 |
| A2 / R1、R5、R8 | 群/话题关系验证、规范 UUID、DM/group/reply 请求体 | 错锚点拒绝，同目标一个决定，固定 UUID 请求契约保持 |
| B1 / R6 | 两个真实同步调用先读 active，依次写 in_review/done；再加入成功/失败竞争 | 首次结构化终态不覆盖，业务终结与配额副作用只发生一次 |
| B2 / R11 | 关联 task 的合成目录/凭据样式错误、正常 issue blocked/cancelled、自定义状态、历史无证据 | 原始错误不外发；合法结构化状态可用；历史如实降级 |
| B3 / R7 | 实际 ScanOnce 路径，两方向修改配置，带 task/issue 关联，空/非空 output | 原来源不会随当前模式改变；空 output 不变成 issue 卡 |
| C1 / R4 | 超过 20,000 个非终态候选，跨 tick、重启、多副本、晚提交旧键、持续新增 | 后排终态能被访问，完整周期能结束，旧代次不能覆盖新游标 |
| C2 / R12 | create_issue 最终 task 失败且事件丢失；另有活跃重试；无关普通 task | 正确恢复关联 run，有重试不提前失败，无关任务不进入该状态机 |
| D1 / R3 | 保存/批准/入队/test-send/回执与删除交错 | 删除提交后不遗留新建的 workspace 子记录 |
| D2 / R9、R10、R13 | 普通与 test-send 的中断、过期、新 owner 认领、旧请求晚返回、多分片重试 | 旧 owner 不发新分片、不覆盖新状态；真实回执可核对，恢复路径可用 |
| E1 / S2 | 两次同库套件运行；清理故障 | 正常无该套件 workspace/member/agent 残留；清理失败时进程非零退出 |

第二次审阅 8 个复現是最小固定回归集；其余表格场景验证同一边界的相邻生产入口。补齐涉及的 handler、messagedelivery、lark/channel/engine、service 配额/终态、普通 Chat、入站 webhook、迁移和 workspace manifest 回归；sqlc 无未提交生成差异。不要仅凭总测试数或手工构造最终快照判定通过。

交付附“验收编号 → 实际测试名/结果 → 代码位置”，全部结果绑定同一最终 SHA。迁移报告区分全新库与从已部署版本升级，记录对既有未批准路由的影响；测试使用独立库。真实飞书联调继续独立列出目标、授权和实际结果，未执行时明确缺口；按议题原文可先提交本地证据，不要求等待 CI，也不擅自合并、部署或发送真实消息。

## 八、复审协议

采用固定范围、固定证据矩阵和一次完整审阅。现有清单以外的维护建议单列，不临时升级为验收条件；新发现的原规格遗漏或本轮引入的回归，必须给出规格依据、生产调用链/可运行复现和影响，集中报告并更新同一矩阵。不能承诺忽略新的真实阻塞，也不重复提出已经被证据关闭的问题。

审阅侧结论：**以上方案具备实施条件；同意按此版系统修复。代码通过与否以最终 SHA 的证据为准。**
