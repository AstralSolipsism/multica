## ③ 数据库、后端与 daemon 性能

- **`ListManagedGitHubInstallationIDsByUser`**：在本机 PostgreSQL 15 上临时建了一个独立库（用完已删除），执行完整迁移后造数：5,000 个工作区、20,000 个用户、60,000 个成员、3,000 条绑定，ANALYZE 后用 `EXPLAIN (ANALYZE, BUFFERS)` 测量。
  - 执行计划：`idx_member_user_workspace` 位图扫描，再以 `(workspace_id, installation_id)` 唯一索引做嵌套循环。
  - **0.18 ms，命中 9 个 shared buffer。**
  - 上游的 `installation_id` 查询为 **0.15 ms，命中 7 个 buffer**。
  - 没有全表扫描，也没有 N+1。
- **GitHub API 扇出**：
  - 复用列表接口会对调用者管理的每个安装**依次**调用 `GET /app/installations/{id}`。每次都重新签发 JWT，单次超时 15 秒。
  - 前端在 Settings 的 Code 和 Repositories 页使用 `staleTime: 0` 并在窗口聚焦时刷新。所以管理 k 个组织的管理员，每次切回窗口都会触发 k 次串行的 GitHub 调用。
  - 只有管理员会遇到，频率低，放入非阻断池：并发上限设为 4，JWT 每次请求只签一次。
- **`9054`**：一次性执行。用到的查询都有索引（`issue` 用 `idx_issue_status(workspace_id, status)`，项目按主键），工作流表很小；不再做 EXPLAIN。
- **daemon 和桌面端**：
  - 工作区根目录只在设置页挂载和 profile 变化时读取一次配置；写入时调用一次 `multica config set`，超时 15 秒。没有轮询。
  - 与 Go 端的优先级逐条对齐：环境变量 > profile 配置 > 默认值，两边都先 trim。
  - 正在运行的任务数复用全局共享的 runtime 和 snapshot 查询。

## ④ 前端请求与体验

TanStack Query 5.96.2 的行为以源码为准：

- 同一个 query 的实际轮询周期，取所有已启用 observer 里最短的那个间隔；
- `refetchInterval` 在标签页隐藏时自动暂停；
- 查询从禁用变回启用时，如果数据已过期会立即补拉。

**三处既有策略的复核**：

- **空闲预热（`route-data-prefetch.tsx`）**：`WARM_ON_IDLE` 为空，首屏不发预热请求。v0.8 没有新增空闲或首屏预取。剩下一个对空数组的空闲回调，不发请求；为了不扩大上游 diff，保持原样。
- **侧栏折叠零请求**：7 个面板组件都已接入。遗漏了 `views-section` 的未读列表：如果用户收藏了“未读”视图，或用了带未读筛选的保存视图，折叠期间每次未读变化都会重拉。**已修复。**
- **已关闭 Issue 停轮询**：原逻辑只覆盖了“没有任何唤醒行”的情况。只要有历史行（包括已停用、已结束的），就会一直每 10 秒轮询，并且照样读取不会展示的系统规则。Issue 右侧栏折叠后内容仍然挂载，两个请求也继续每 10 秒一次。**已修复。**

**全仓轮询复核新发现**：

- **Fork 主机指标给共享的 `runtimeListOptions` 加了 30/60 秒轮询。**
  - 应用外壳的 `WorkspacePresencePrefetch` 一直订阅着这个列表（web、桌面主窗口、每个独立 Issue 窗口都有）。所以每个窗口在任何页面都按这个频率请求。
  - 实际上只有 Runtimes 列表和 Runtime 详情两个页面展示主机指标；runtime 的上下线已经由 WS 事件更新。
  - **已改为只在这两个页面带轮询**，其他页面回到上游行为。这两个页面的刷新频率不变。
- **其余发现大多来自上游原有代码或其他功能单位**，修改会扩大 diff，或者需要业务确认。逐条放入非阻断池；需要确认业务假设的一条见 B2。

**体验**：

- 飞书群二维码弹窗的宽度固定，背景为白色。二维码需要白底，暗色模式下可以接受。
- GitHub 回调的错误码都映射到了本地化文案。无法自行恢复的两类提示会常驻，并带关闭按钮。
- 桌面端写入工作区根目录失败时，主进程返回的两句英文（CLI 未安装、等待服务地址）会原样出现在 toast 的说明里，没有本地化。放入非阻断池。
- 本次没有在浏览器或桌面端截图走查，以上结论来自代码和单测。

B2 的落地方式：
- 每一行的投递查询，在运行已结束（completed、failed、skipped）满 10 分钟、且第一页没有 `queued` 或 `sending` 的投递时，就停止轮询（`runDeliveriesRefetchInterval`）。
- 依据如下：
  - 自动重试会把投递重新置为 `queued`，所以仍按 5 秒刷新；
  - 补偿器每 30 秒扫描一次，漏掉的投递会在运行结束后约 1 分钟内补上；
  - 新加的路由不会给 `effective_from` 之前已结束的运行补发。
- 运行结束后，状态只会因为手动重试而变化。点重试的人，自己的页面会立即刷新；同一时间开着该页面的其他人，需要刷新页面才能看到变化。
- 运行未结束（包括 `issue_created`）或缺少完成时间时，保持原来 30 秒的刷新。
