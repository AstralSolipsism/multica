# 自适应存为 `thinking_level` 的保留值 `_adapt`

自适应是第三种挡位设定，另外两种是跟随 CLI 配置（`thinking_level` 为空）和固定挡位（其他取值）。负责人 2026-10-21 在 OL-992 中决定（D1、D2）：不新增字段，把自适应存为 `thinking_level` 的保留值 `_adapt`；外发采用零配置，不设开关。

## 理由

- **不新增字段。** `thinking_level` 已经是"思考"属性唯一的存储，自适应只是它的第三种取值。校验、领取、复制、清理和界面都沿用这一个字段，不必维护两个字段之间的组合规则，用户看到的也仍是一个选择器。
- **前导下划线。** 保留值既不能是任何 CLI 可能使用的挡位，也不能和已存的数据冲突。
  - `auto` 已被占用：reasonix 的目录里有 `auto`，服务端照常保存它；dim 的会话也报告 `auto`；omp 的 `--thinking` 同样接受 `auto`。
  - `adapt` 这样的普通单词也不安全：OpenCode 允许用户在 `opencode.json` 里自定义 variant 名。
  - 服务端从不接受以符号开头的挡位。动态目录和 ACP 目录的取值要通过 `isValidDynamicThinkingValue`，它拒绝以 `-`、`_`、`.` 开头的值；固定词表里也没有这样的值。所以已存的数据里不会有 `_adapt`，存储里的 `_adapt` 只能表示自适应。
  - 用下划线而不用 `*`：`*` 是 shell 通配符，zsh 下不加引号会直接报错，而人和智能体都会在命令行里写这个值。
- **旧 daemon 不受影响。** 旧 daemon 会把不认识的挡位原样交给 CLI。只有领取请求带了能力位 `thinking-adapt-v1`，服务端才下发 `_adapt`；否则改写为空值，旧 daemon 就按跟随 CLI 配置执行。
- **外发零配置。** 选择自适应即表示同意把脱敏、截断后的运行摘要发给决策引擎，不另设字段或工作区开关。选项说明写明发送什么、发给谁（默认是 OpenCode Zen 免费通道）。机器主人可以在本机设置 `MULTICA_JEV_DISABLED=1` 关闭，此时自适应一律回退。

## 考虑过的方案

- **新增字段 `thinking_mode`**：架构师最初的推荐。它不占用 `thinking_level` 的取值，旧 daemon 也天然读不到。负责人否决：多一个字段会增加修改复杂度和用户的理解成本，而它要解决的两个问题，前导下划线和能力位改写已经解决了。
- **工作区开关**（默认关闭，只有 owner/admin 能打开）：daemon 此前不会自己把运行内容发给第三方服务，所以考虑过要求显式授权。负责人选择零配置。

## 后果

- 凡是按挡位处理 `thinking_level` 的地方，都要先识别 `_adapt`：
  - 服务端校验在现有的挡位校验之前判断它；
  - 换模型时按新模型的候选挡位决定保留还是清空，不能在新模型的挡位列表里查找它；
  - 界面显示"自适应"，不显示 `_adapt`。
- 即使服务端误发，daemon 也保证 `_adapt` 不进入任何 CLI 参数或 ACP 调用。
- 以后如果改用独立字段，需要迁移已存的 `_adapt`，并同时修改服务端、daemon 和各个客户端。
