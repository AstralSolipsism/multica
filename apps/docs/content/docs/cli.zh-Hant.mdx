Multica CLI 既負責連接本機運行時，也可以在終端中管理工作區、任務、智能體和自動化。這裏介紹常用路徑；當前版本支持的參數始終以命令自身的 `--help` 爲準。

## 安裝

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

```bash
curl -fsSL https://multica.outlune.com/downloads/install.sh | bash
```

</Tab>
<Tab value="Windows">

從內部發布源 `https://multica.outlune.com/downloads/cli/v<version>/`（版本號見
`https://multica.outlune.com/downloads/latest.json`）下載對應 release 的
`multica-cli-<version>-windows-<arch>.zip` 壓縮包，解壓出 `multica.exe` 並放入
`PATH`。

</Tab>
</Tabs>

確認安裝成功：

```bash
multica version
```

## 第一次連接

按連接的服務選擇：

<Tabs items={["Multica Cloud", "自託管實例"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="自託管實例">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup` 會保存服務地址、打開瀏覽器完成登錄，並啓動守護進程。完成後檢查：

```bash
multica auth status
multica daemon status
```

如果只需要重新登錄，不想覆蓋其他配置，運行 `multica login`。沒有瀏覽器的環境可以先在 Web 設置中創建個人訪問令牌，再輸入：

```bash
multica login --token
```

命令會在終端中提示粘貼令牌，避免把完整值留在 shell history 中。

## 選擇工作區

列出並切換默認工作區：

```bash
multica workspace list
multica workspace switch <slug>
```

之後的命令會使用這個工作區。單次命令可以通過 `--workspace-id` 臨時覆蓋，也可以設置 `MULTICA_WORKSPACE_ID`。

邀請成員：

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## 常用任務操作

```bash
# 查看和搜索
multica issue list
multica issue get MUL-123
multica issue search "登錄失敗"

# 創建和修改
multica issue create --title "修復登錄失敗"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# 評論和執行記錄
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "請先檢查迴歸測試"
multica issue comment update <comment-id> --expected-revision 2 --content "請檢查迴歸測試和發佈說明"
multica issue runs MUL-123
```

長描述或評論從 stdin 讀取，避免處理換行和引號：

```bash
multica issue create --title "升級說明" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

查看某次運行的消息、停止運行或重試：

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123
multica issue rerun-task <run-id> --issue MUL-123 --fresh
```

把評論插話到仍在進行中的運行，而不是排隊一個後續運行（僅限支持插話的運行；你的評論能啓動哪個智能體，就能向它插話）：

```bash
multica issue comment add MUL-123 --content-file note.md --steer <task-id>
multica issue comment add MUL-123 --content-file note.md --steer-active
```

同一項目、同一父任務下已有標題相同（不區分大小寫，忽略多餘空格）且未關閉的任務時，`issue create` 會拒絕創建並給出那個任務。確實要再建一個，加 `--allow-duplicate`；要把一個任務標爲另一個的重複，用 `multica issue status MUL-124 cancelled --duplicate-of MUL-123`。

### 時間線

`issue get` 給出任務現在的狀態；`issue timeline` 按時間順序列出狀態、優先級、負責人、標題、日期的改動和運行結果，並混排評論，用來回答"什麼時候進入 in_review""卡在當前狀態多久了"：

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only` 去掉評論，保留全部活動記錄；`--action` 只返回指定的動作，可重複，並隱含 `--activity-only`。服務器讀取的歷史有上限，被截斷時 stderr 會打印警告，這時不要據此推算停留時長。

### 讀長評論線程

評論多的任務，智能體逐條讀取很費 token。先掃一遍線程，再展開需要的那一個：

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only` 只返回頂層評論，每條附帶回複數和最近活動時間。
- `--summary` 把每條內容截成預覽。
- `--compact` 只作用於 JSON 輸出，去掉不帶信息的字段（例如重複的 `issue_id`、空數組）。
- `--recent N` 返回最近活躍的 N 個線程，每個線程帶上全部回覆，回覆多時輸出可能很長。
- 已解決的線程默認摺疊成首條評論和結論，需要原文時加 `--full`。

列表也可以只取需要的字段：`multica issue list --output json --fields id,identifier,title,status`。篩選在 CLI 本地完成，減少的是輸出和上下文，不是請求量。

按最近更新時間列出任務時，同時傳入 RFC3339 時間戳 `--updated-since` 和 `--updated-until`。服務端返回當前 `updated_at` 大於等於 `since`、小於 `until` 的任務，即 `[since, until)`。這兩個參數可與現有篩選、排序和分頁參數組合使用。翻頁時保持時間範圍一致；分頁不提供快照，併發更新可能改變結果集。

```bash
multica issue list --updated-since 2026-11-05T10:00:00Z \
  --updated-until 2026-11-05T10:01:00Z \
  --sort created_at --direction asc --limit 100 --offset 0 \
  --output json --fields id,workspace_id,project_id,title
```

### 喚醒

喚醒讓智能體在某個事件發生、某個條件成立或到點時開始一次普通運行。完整規則見[任務喚醒](/issue-wakeups)。

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "對方回覆後，按回復內容更新報價單"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "檢查供應商是否回信"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

在終端裏以成員身份創建時需要 `--agent-id`；智能體在自己的運行中創建時默認喚醒它自己。

## 智能體和 skill

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

導入時遇到同名 skill，默認會停止且不修改現有內容。按意圖選擇：

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite` 只允許 skill 的創建者使用，並保留原來的 ID 與智能體綁定關係。

環境變量和 MCP 配置常帶有 token。命令行裏直接寫值會留在 shell 歷史和 `ps` 輸出中，用 `-file` 或 `-stdin` 形式傳入：

```bash
multica agent create --name "運營助手" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- `--custom-env` 系列只在 `agent create` 中可用。之後修改用 `agent env set`，它整體替換原有變量，值寫成 `****` 的鍵保留原值。
- `agent update --mcp-config null` 清除 MCP 配置。
- `--custom-args` 是 JSON 數組，排在啓動參數的最後。選模型用 `--model`，部分工具會拒絕出現在自定義參數裏的 `--model`。
- 誰能調用智能體用 `--permission-mode`：`private` 只有所有者，`public_to` 配合 `--public-to-workspace` 或 `--public-to-member <user-id>`。`--visibility private|workspace` 是舊寫法，會映射到 `--permission-mode`；兩者同時給出時以 `--permission-mode` 爲準。

## 守護進程和運行時

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

```bash
multica daemon autostart enable
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "內部 Claude 封裝" \
  --command-name ccms --runtime-type claude
```

`daemon autostart` 爲當前 profile 登記開機自啓，平臺差異見[開機自啓](/daemon-runtimes#autostart)。`runtime usage` 默認統計 90 天，`--days` 最多 365。`runtime update` 讓那臺電腦上的守護進程把 CLI 更新到指定版本，`--wait` 會一直等到更新結束。`runtime profile create` 用 `--runtime-type` 指定兼容的工具（舊的 `--protocol-family` 仍可用）；固定參數目前只能在網頁端填寫。

刪除仍綁定活躍智能體的運行時時，命令默認拒絕。`multica runtime delete <id> --cascade` 會解綁這些智能體、保留其配置與歷史記錄，並取消它們的活動運行。

運行機制和自定義 profile 見[守護進程與運行時](/daemon-runtimes)。

## 項目、工作區和自動化

```bash
multica project create --title "618 活動" --lead "李雷" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "運營部" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "每週銷售週報" --agent "運營助手" \
  --mode create_issue --issue-title-template "銷售週報 {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Asia/Shanghai
```

- `--lead` 接受成員或智能體的名稱。`--default-branch-hint` 只告訴智能體倉庫的默認分支，不會切換分支。
- 工作區的 `--context` 會提供給工作區裏的每個智能體。`--slug` 創建後不能修改；`--issue-prefix` 會轉成大寫，修改它會給所有現有任務重新編號，外部引用裏的舊編號隨之失效。
- `--issue-title-template` 只替換 `{{date}}`（UTC，`YYYY-MM-DD`），其他 `{{...}}` 會被拒絕。定時觸發器的 `--timezone` 默認 UTC。

## ID 和輸出格式

任務使用 `MUL-123` 這樣的 key 或完整 UUID，不接受 UUID 短前綴。

其他資源的 `list` 命令通常顯示可複製的短 ID，並支持 `--full-id` 輸出完整 UUID。短 ID 不唯一時，CLI 會要求增加字符或改用完整 UUID。運行的短 ID 還需要通過 `--issue` 指明所屬任務。

許多命令支持結構化輸出：

```bash
multica issue list --output json
multica agent list --output json
```

腳本使用 JSON 輸出，不解析面向終端的表格。各命令支持的輸出格式和分頁參數以 `multica <command> --help` 爲準。

## Profile 與配置

默認配置保存在 `~/.multica/config.json`。使用 `--profile <name>` 可以隔離另一套服務地址、令牌、默認工作區和守護進程狀態：

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

命名 profile 保存在 `~/.multica/profiles/<name>/config.json`。查看當前值：

```bash
multica config show
multica config show --profile staging
```

<Callout type="warning">
CLI 配置文件包含可代表你訪問 Multica 的令牌。不要提交到倉庫、上傳到日誌或與他人共享。
</Callout>

## 命令參考

下表覆蓋當前全部頂層命令，按 CLI 自身的分組排列。所有命令都接受全局 flag `--server-url`、`--workspace-id`、`--profile` 和 `--debug`。`--output` 是逐命令註冊的 flag，默認格式因命令而異：`list` 類默認表格，`get`、`create` 類多默認 JSON。完整參數以 `multica <command> --help` 爲準。

### 任務附件

`issue create`、`issue update` 和 `issue comment add` 的每個 `--attachment` 接受一個完整文件路徑，保留文件名中的逗號和雙引號。多個文件須重複 flag，例如 `--attachment 'report,final.csv' --attachment notes.txt`。省略 flag 時不添加附件；顯式傳入空路徑會報錯。所有本地路徑都通過檢查後纔開始上傳。

從舊 CSV 解析方式遷移：要添加兩個文件，將 `--attachment a,b` 改爲 `--attachment a --attachment b`。前一種寫法現在只選擇名爲 `a,b` 的單個文件。舊用法 `--attachment '"report,final.csv"'` 中額外的 CSV 雙引號也須移除，改用 `--attachment 'report,final.csv'`；只有文件名本身包含雙引號時才保留。

## 在其他編碼智能體裏操作 Multica

如果你的工作大多發生在 Codex、Claude Code 或 Cursor 裏，可以直接在那裏操作 Multica，不必切回終端。[Multica CLI skill](https://github.com/multica-ai/multica-cli) 會教這些智能體安全地使用本頁的命令：讀任務和評論線程時少耗 token、通過文件寫評論，以及正確處理 mention、狀態變更和指派帶來的副作用。

它完全通過你已認證的 CLI 運行，本身不授予任何權限，權限仍然只來自你的登錄、所選 profile 和工作區。要求 CLI 版本不低於 v0.4.26。該倉庫的 README 說明了 Claude Code 插件市場、Codex skill 安裝器、Cursor 以及其他任何加載 Markdown 指令的工具的安裝方式。

## 在任務中調用受管評分

運行中的智能體任務可調用平臺決策服務，對業務內容評分：

```bash
multica jev evaluate --input-file evaluation.json --output json
```

`--input-file -` 從標準輸入讀取。JSON 包含 `state`（對象或字符串）及 `questions`；後者按問題名組織，每題填寫 `type: "score"`、`instructions` 和有序 `criteria` 數組。原始分數從零到最後一項標準的下標。來源、模型與憑據由 daemon 統管，調用方不配置基礎設施；CLI 與 daemon 都須升級到支持此命令的版本。

成功 JSON 含 `ok: true`、`answers`、`latency_ms` 和 `daemon_version`。未完成評分時命令以非零退出，不能記作評分通過。輸入文字會發往 daemon 已配置的決策服務。
